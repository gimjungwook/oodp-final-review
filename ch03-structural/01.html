Sub-Chapter 01 · 구조 패턴

    어댑터 패턴,
    맞지 않는 인터페이스를 끼워 맞추다

    잘 동작하는 외부 코드가 있는데 내 시스템이 기대하는 모양과 다르다. 원본을 고칠 수는 없다. 어댑터는 그 사이에 변환기를 끼워, 서로 모르던 두 인터페이스를 협력하게 만든다.

    어댑터 패턴(Adapter Pattern)의 의도는 한 문장이다. 한 클래스의 인터페이스를 클라이언트가 기대하는 다른 인터페이스로 변환한다. 인터페이스 불일치 때문에 함께 쓸 수 없던 클래스들을, 변환 계층 하나로 협력하게 만드는 것이 목적이다. 핵심 단어는 변환(convert)이다. 기능을 더하거나 빼는 것이 아니라, 같은 기능을 다른 모양의 호출로 바꿔 전달한다.

    왜 필요한가? 현실의 코드는 처음부터 한 사람이 한 규칙으로 짠 것이 아니다. 이미 검증된 외부 라이브러리(legacy library)나 서드파티 모듈은 자기만의 메서드 이름과 인자 구조를 가진다. 그런데 내 시스템은 일관된 인터페이스를 기대한다. 예를 들어 외부 라이브러리는 LegacyRectangle.display(x1, y1, x2, y2)를 제공하는데, 내 코드는 모든 도형을 Shape.draw()로 그리도록 설계돼 있다. 라이브러리 원본은 손댈 수 없다(소스가 없거나, 고치면 다른 곳이 깨진다). 이때 둘 사이에 변환기를 끼워 불일치를 흡수하는 것이 어댑터다.

    해외여행용 전원 어댑터. 한국 노트북 플러그(클라이언트가 기대하는 인터페이스)를 유럽 콘센트(외부 시스템의 인터페이스)에 그대로 꽂을 수 없다. 그렇다고 노트북 플러그를 잘라 고치거나 벽의 콘센트를 뜯을 수는 없다. 대신 사이에 전원 어댑터를 끼운다. 어댑터는 전기 자체를 바꾸지 않는다(기능은 그대로) — 단지 모양만 한쪽에서 받아 다른 쪽 모양으로 내보낸다. 소프트웨어 어댑터가 하는 일이 정확히 이것이다.

    구조 — 위임으로 모양을 바꾼다

    객체 어댑터(object adapter)는 세 역할로 구성된다. Target은 클라이언트가 기대하는 인터페이스(request())다. Adaptee는 이미 존재하지만 모양이 다른 기존 클래스(specificRequest())다. Adapter는 Target을 구현하면서, 내부에 Adaptee를 멤버로 품는다(합성). 클라이언트가 request()를 부르면, Adapter는 그 호출을 자기가 품은 adaptee.specificRequest()로 위임(delegate)하면서 인자나 형식을 변환해 넘긴다. 클라이언트는 Adaptee의 존재조차 모른 채 익숙한 request()만 쓴다.

    UML 01객체 어댑터 클래스 다이어그램 · 합성으로 Adaptee를 품는다
    classDiagram
    class Target {
        +request()
    }
    class Adapter {
        -adaptee : Adaptee
        +request()
    }
    class Adaptee {
        +specificRequest()
    }
    Target <|.. Adapter
    Adapter o--> Adaptee : 위임

    Adapter는 Target을 구현(점선 실현 화살표)하면서 동시에 Adaptee를 합성(o--> 마름모)한다. request() 안에서 품은 adaptee의 specificRequest()를 불러 변환한다. 이 "구현 + 합성" 조합이 객체 어댑터의 시각적 표식이다.

    코드 — request()가 specificRequest()로 위임된다

    핵심 메커니즘은 단순하다. Adapter의 request() 본문에서 품은 adaptee의 메서드를 호출해 결과를 돌려준다. 인터페이스가 다른 만큼, 이름과 인자 구조를 맞춰 주는 변환 코드가 그 사이에 들어간다. 아래는 모양이 다른 LegacyRectangle을 Shape로 끼워 맞추는 예다.

    CODE 01객체 어댑터 (합성 + 위임)
    interface Shape {                       // Target: 클라이언트가 기대하는 인터페이스
    void draw(int x, int y, int w, int h);
}

class LegacyRectangle {                  // Adaptee: 모양이 다른 기존 클래스
    void display(int x1, int y1, int x2, int y2) { /* 외부 라이브러리 */ }
}

class RectangleAdapter implements Shape {
    private final LegacyRectangle adaptee;          // 합성: Adaptee를 멤버로 품는다
    RectangleAdapter(LegacyRectangle a) { this.adaptee = a; }

    public void draw(int x, int y, int w, int h) {  // Target 인터페이스 구현
        adaptee.display(x, y, x + w, y + h);        // 위임 + 인자 변환 (w,h → x2,y2)
    }
}

// 클라이언트는 Shape만 알면 된다 — Adaptee의 존재를 모른다
Shape s = new RectangleAdapter(new LegacyRectangle());
s.draw(10, 20, 100, 50);

    클라이언트는 익숙한 draw(x,y,w,h)만 호출한다. Adapter가 너비·높이를 좌표쌍(x2,y2)으로 변환해 adaptee.display()로 넘긴다. 클래스 어댑터(다중 상속 기반)도 있으나, 다중 상속이 없는 자바에서는 이처럼 합성 기반 객체 어댑터가 표준이다.

    참여자와 결과

    참여자

    Target(기대 인터페이스), Adaptee(기존 클래스), Adapter(변환 계층, Adaptee를 합성)

    장점

    원본을 고치지 않고 재사용, 인터페이스 불일치 흡수, 클라이언트와 Adaptee 분리

    단점

    변환 계층만큼 코드 증가, 변환이 복잡하면 어댑터가 무거워짐

    시험 함정. Adapter vs Decorator — 둘 다 객체를 합성으로 감싸지만 목적이 정반대다. 어댑터는 인터페이스를 바꾸는 것(목적: 호환)이고, 데커레이터는 인터페이스를 유지한 채 기능을 더하는 것(목적: 확장)이다. 즉 어댑터는 모양을 바꾸고 기능은 그대로, 데커레이터는 모양은 그대로 두고 기능을 보탠다. 또 객체 어댑터(합성)와 클래스 어댑터(상속)의 차이도 자주 출제된다 — 자바는 합성 기반이 기본이다.

    어댑터가 "모양만 바꾸는" 변환기라면, 다음 sub-chapter의 데커레이터는 모양은 그대로 유지하면서 기능을 동적으로 덧붙이는 껍질이다. 두 패턴이 같은 합성·위임 무기를 쓰면서도 완전히 다른 목적을 푼다는 점이, 구조 패턴을 이해하는 출발점이다.
