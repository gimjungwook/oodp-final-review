Sub-Chapter 01 · 생성 패턴

    싱글톤 패턴,
    오직 하나만 존재하게

    시스템 전체가 공유해야 하고 둘 이상 존재하면 충돌이 나는 자원이 있다. 설정 관리자, 로그 기록기, 프린터 스풀러, 커넥션 풀. 싱글톤은 이 "유일성"을 클래스 스스로가 보장하게 만든다.

    싱글톤 패턴(Singleton Pattern)의 의도는 한 문장이다. 어떤 클래스의 인스턴스가 오직 하나만 존재하도록 보장하고, 그 하나에 대한 전역 접근점(global access point)을 제공한다. 핵심은 두 부분으로 나뉜다. "하나만"이라는 유일성 보장과, "어디서나 가져다 쓸 수 있는" 전역 접근이다. 이 둘을 모두 클래스 자신이 책임진다는 점이 싱글톤의 정체성이다.

    왜 필요한가? 시스템에는 본질적으로 하나여야 하는 것들이 있다. 애플리케이션 설정(AppConfig)이 두 개라면 한쪽을 바꿔도 다른 쪽은 옛 값을 들고 있어 충돌한다. 로그 파일에 두 객체가 동시에 쓰면 줄이 엉킨다. 이런 자원을 전역 변수(global variable)로 두면 누구나 마음대로 덮어쓸 수 있고, 언제 생성되는지 통제할 수 없다. 싱글톤은 생성 자체를 클래스가 통제하게 만들어 이 문제를 푼다.

    한 나라의 대통령. 어느 시점에 대통령은 정확히 한 명이어야 한다. 두 명이 동시에 명령을 내리면 국가가 혼란에 빠진다. 그리고 누구든 "대통령"을 부르면 같은 사람을 가리킨다(전역 접근점). 새 대통령을 아무나 마음대로 임명할 수 없고, 정해진 절차(헌법 = private 생성자 + getInstance)로만 결정된다. 싱글톤이 정확히 이 구조다.

    구조 — 어떻게 유일성을 강제하는가

    메커니즘은 세 가지 장치의 조합이다. 첫째, 생성자를 private으로 막아 외부에서 new로 또 만들 수 없게 한다. 둘째, 유일 인스턴스를 static 필드에 보관한다(클래스당 하나만 존재하는 자리). 셋째, 그 인스턴스를 돌려주는 static getInstance() 메서드로만 접근하게 한다. 외부는 생성 통로가 막혀 있고, 오직 이 한 문으로만 들어온다.

    화살표가 자기 자신을 향하는 것이 싱글톤의 시각적 표식이다. 생성자(−Singleton())는 private이고, 외부는 +getInstance()로만 그 하나에 접근한다.

    코드 — 지연 초기화와 멀티스레드 함정

    가장 단순한 형태는 처음 요청될 때 만들고(지연 초기화, lazy initialization) 이후 재사용하는 것이다. 그런데 이 단순한 형태가 멀티스레드(multi-thread) 환경에서 깨진다. 두 스레드가 동시에 if(instance==null)를 통과하면 인스턴스가 두 번 만들어진다. 그래서 이중 검사 잠금(Double-Checked Locking)과 volatile을 함께 쓴다.

    CODE 01이중 검사 잠금 싱글톤 (스레드 안전)
    public class AppConfig {
    private static volatile AppConfig instance;   // volatile: 가시성 보장
    private AppConfig() {}                          // 외부 생성 차단

    public static AppConfig getInstance() {
        if (instance == null) {                     // 1차 검사 (락 없이, 빠름)
            synchronized (AppConfig.class) {
                if (instance == null) {             // 2차 검사 (락 안, 안전)
                    instance = new AppConfig();
                }
            }
        }
        return instance;
    }
}

    1차 검사는 락 비용을 피하려는 빠른 경로, 2차 검사는 경쟁 상황에서 중복 생성을 막는 안전장치다. volatile이 없으면 부분 초기화된 객체가 다른 스레드에 보일 수 있다. 더 간단한 대안으로 정적 초기화(eager) 나 enum 싱글톤도 자주 쓴다.

    참여자와 결과

    참여자

    Singleton (private 생성자, static instance, getInstance)

    장점

    유일성 보장, 전역 접근, 지연 초기화 가능, 자원 절약

    단점

    전역 상태로 결합도 증가, 의존성이 숨겨져 테스트 곤란

    시험 함정. ① 단순 if(instance==null)는 멀티스레드에서 인스턴스를 둘 만들 수 있다 — 이중 검사 잠금 + volatile, 또는 eager/enum으로 푼다. ② "전역 접근점" 때문에 의존성이 코드에 드러나지 않아 테스트와 결합도 면에서 안티패턴이라는 비판도 단골 출제 포인트다. ③ 싱글톤의 시각적 표식은 "자기 자신을 가리키는 연관"이다.

    싱글톤은 생성 횟수를 통제하는 가장 단순한 생성 패턴이다. 다음 sub-chapter의 팩토리 메서드는 한 걸음 더 나아가 "무엇을 만들지"의 결정 자체를 서브클래스로 넘긴다. 두 패턴 모두 new를 사용하는 코드로부터 생성 책임을 떼어 낸다는 같은 목표를 공유한다.
