Sub-Chapter 03 · 행위 패턴

    커맨드 패턴,
    요청을 객체로 포장하다

    리모컨 버튼은 무엇을 켜는지 몰라도 동작한다. "조명을 켜라"는 요청을 객체로 만들면, 그 요청을 변수에 담고, 큐에 쌓고, 로그로 남기고, 되돌릴(undo) 수 있다. 커맨드는 호출하는 쪽과 실제 일하는 쪽 사이에 "요청 객체"를 끼워 넣는다.

    커맨드 패턴(Command Pattern)의 의도는 이렇다. 요청(request)을 하나의 객체로 캡슐화한다. 그러면 서로 다른 요청으로 클라이언트를 매개변수화하고, 요청을 큐에 넣거나 로그로 기록하며, 실행 취소(undo)가 가능한 연산을 지원할 수 있다. 보통 메서드 호출은 "그 자리에서 즉시" 일어나고 사라진다. 커맨드는 그 호출 행위 자체를 일급 객체(first-class object)로 만들어, 변수에 담고 나중에 실행하고 되돌릴 수 있는 "다룰 수 있는 것"으로 바꾼다.

    왜 필요한가? 버튼이 직접 light.on()을 부르면, 그 버튼은 "조명을 켠다"는 일에 영원히 묶인다. 버튼을 선풍기에 재활용하려면 코드를 고쳐야 하고, 매크로(여러 동작을 한 번에)나 실행 취소를 붙이려면 버튼마다 그 로직을 욱여넣어야 한다. 호출하는 쪽(Invoker, 버튼)과 실제 일하는 쪽(Receiver, 조명)이 직접 손잡으면 강하게 결합되기 때문이다. 커맨드는 그 사이에 요청 객체(Command)를 끼운다. 버튼은 이제 "무엇을 누가 하는지" 모른 채 그저 command.execute()만 부른다. 호출 시점과 실행 내용이 분리되는 것이다.

    식당의 주문서. 손님(클라이언트)이 "파스타 하나"라고 말하면 종업원은 그 요청을 주문서(Command)에 적는다. 종업원(Invoker)은 주문서를 주방에 걸 뿐, 파스타를 어떻게 만드는지 모른다. 요리사(Receiver)가 주문서를 보고 실제로 요리한다. 주문서는 객체이므로 줄을 세워 큐에 쌓을 수 있고("3번 테이블 먼저"), 보관해 두었다가 나중에 처리할 수 있고, 잘못된 주문은 취소표를 붙여 되돌릴 수 있다. 요청을 종이 한 장으로 객체화했기에 이 모든 게 가능하다 — 커맨드가 정확히 이 발상이다.

    구조 — 네 역할과 화살표의 방향

    커맨드는 네 역할이 정확히 맞물려야 한다. Command는 execute()(와 undo())를 선언한 인터페이스다. ConcreteCommand는 그 인터페이스를 구현하되, 자기가 부려 먹을 Receiver를 필드로 들고 있다가 execute()에서 receiver.action()을 부른다. Invoker는 Command 참조만 보관하고 때가 되면 command.execute()를 호출한다 — 어떤 구체 명령인지, 누가 실제로 일하는지는 모른다. Receiver는 진짜 작업(action())을 수행하는 객체다.

    화살표 방향이 시험의 핵심이다. Invoker → Command (인보커는 커맨드 인터페이스에 의존, 합성으로 보유). ConcreteCommand → Receiver (구체 명령이 리시버를 알고 위임). ConcreteCommand ..|> Command (구체 명령이 인터페이스를 구현). 즉 인보커는 인터페이스만 알고, 리시버를 아는 것은 오직 ConcreteCommand뿐이다. 이 방향이 뒤집히면 결합이 깨지므로, 도식을 외울 때 "인보커는 커맨드로, 구체커맨드는 리시버로"를 입에 붙여 두자.

    코드 — 실행, 그리고 되돌리기

    리모컨(Invoker)이 조명(Receiver)을 켜는 예다. LightOnCommand가 조명을 들고 있고, execute()는 켜기, undo()는 그 역연산인 끄기를 한다. 실행한 명령을 스택에 쌓아 두면 마지막 동작을 되돌릴 수 있다.

    CODE 01리모컨 커맨드 (execute / undo)
    interface Command {
    void execute();
    void undo();
}

class Light {                       // Receiver — 실제 일하는 객체
    void on()  { System.out.println("조명 ON"); }
    void off() { System.out.println("조명 OFF"); }
}

class LightOnCommand implements Command {  // ConcreteCommand
    private final Light light;       // Receiver를 들고 있다
    LightOnCommand(Light light) { this.light = light; }
    public void execute() { light.on(); }   // 위임
    public void undo()    { light.off(); }  // 역연산
}

class RemoteButton {                 // Invoker — Command만 안다
    private final Deque<Command> history = new ArrayDeque<>();
    private Command command;
    void setCommand(Command c) { this.command = c; }
    void press()    { command.execute(); history.push(command); }
    void pressUndo(){ if (!history.isEmpty()) history.pop().undo(); }
}

// 조립 — 클라이언트가 Receiver를 Command에 묶고 Invoker에 꽂는다
Light light = new Light();
RemoteButton btn = new RemoteButton();
btn.setCommand(new LightOnCommand(light));
btn.press();      // 조명 ON
btn.pressUndo();  // 조명 OFF (되돌리기)

    RemoteButton(Invoker)은 Light(Receiver)의 존재를 전혀 모른다 — Command만 안다. 매크로는 여러 Command를 리스트로 묶어 execute()에서 차례로 부르는 한 개의 MacroCommand로, 작업 큐는 Command 객체를 큐에 쌓아 두었다 꺼내 실행하는 방식으로 자연스럽게 확장된다.

    참여자와 결과

    참여자

    Command(execute/undo 인터페이스), ConcreteCommand(Receiver 보유 + 위임), Invoker(Command 보유 + 호출), Receiver(실제 작업)

    장점

    호출-실행 분리로 결합 완화, undo/redo, 매크로, 작업 큐·로그, 요청을 일급 객체로 전달

    단점

    명령마다 클래스가 늘어 구조가 무거워질 수 있음, undo 구현 시 상태 보존 부담

    시험 함정. ① 네 역할(Command / ConcreteCommand / Invoker / Receiver)을 정확히 구분해야 한다 — 특히 "Receiver를 아는 것은 ConcreteCommand뿐, Invoker는 Command만 안다". ② 화살표 방향: Invoker → Command, ConcreteCommand → Receiver. 인보커가 리시버를 직접 가리키면 오답. ③ 핵심 키워드는 "요청을 객체로 만든다". ④ 대표 활용은 undo/redo, 매크로(여러 Command 묶음), 작업 큐, 실행 로그.

    다음으로 — 옵서버 패턴

    커맨드가 "하나의 요청"을 객체로 포장해 호출자와 수행자를 떼어 놓았다면, 다음 sub-chapter의 옵서버 패턴(Observer Pattern)은 "상태 변화의 통보"를 구조화한다. 한 주제(Subject)가 바뀌면 그것을 구독하는 여러 관찰자(Observer)에게 자동으로 알림이 가는 일대다 관계다. 커맨드가 호출의 결합을 끊었듯, 옵서버는 통보의 결합을 끊는다 — 주제는 누가 듣는지 구체적으로 알지 못한 채 그저 "바뀌었다"고 외칠 뿐이다.
