Course C · UML 손그림

    화살표로,
    관계를 증명하기

    패턴의 정답은 "어떤 클래스가 있다"가 아니라 "어떤 관계(상속/구현/합성)가 어느 방향으로 걸려 있다"이다. 세 문제를 종이에 직접 그린 뒤, 정답 다이어그램과 화살표 방향까지 대조하라.

    UML 채점에서 점수는 박스가 아니라 화살표에서 갈린다. 상속(<|-- 실선 빈 삼각형), 인터페이스 구현(<|.. 점선 빈 삼각형), 합성/연관(o--> 보유 후 위임)을 구분해 그려야 한다. 같은 박스 구성이라도 화살표 방향과 종류가 다르면 다른 패턴이다 — 특히 Strategy와 State는 구조가 같아서 주석으로만 갈린다. 먼저 그리고, 펼친 정답과 한 획씩 대조하라.

    C1

    스트래티지(Strategy) vs 스테이트(State)

    두 패턴의 클래스 다이어그램을 나란히 그리고, 구조는 같은데 무엇이 다른지를 화살표/주석으로 표시하라.

    정답 보기 ▸ C1
    UML C1구조는 동일, 의미는 다름
    Strategy — 외부가 전략을 선택
    classDiagram
    class Context {
        -strategy : Strategy
        +setStrategy(s)
        +execute()
    }
    class Strategy {
        <<interface>>
        +algorithm()
    }
    class ConcreteStrategyA {
        +algorithm()
    }
    class ConcreteStrategyB {
        +algorithm()
    }
    Context o--> Strategy : 합성, 위임
    Strategy <|.. ConcreteStrategyA
    Strategy <|.. ConcreteStrategyB
    State — 상태가 다음 상태로 전이
    classDiagram
    class Context {
        -state : State
        +setState(s)
        +request()
    }
    class State {
        <<interface>>
        +handle(ctx)
    }
    class ConcreteStateA {
        +handle(ctx)
    }
    class ConcreteStateB {
        +handle(ctx)
    }
    Context o--> State : 합성, 위임
    State <|.. ConcreteStateA
    State <|.. ConcreteStateB
    ConcreteStateA --> ConcreteStateB : ctx.setState 전이
    채점 포인트

    두 다이어그램 모두 Context o--> 인터페이스(합성, 위임) 골격이 동일해야 한다. 박스만 그려서는 둘을 구분할 수 없다는 점이 핵심.

    차이는 두 곳. ① 누가 선택하는가 — Strategy는 외부(클라이언트)가 setStrategy로 고르고, State는 ConcreteState가 ctx.setState로 스스로 다음 상태를 정한다. ② 구체끼리의 관계 — 전략들은 서로 모르지만(연결선 없음), 상태들은 전이 화살표(ConcreteStateA --> ConcreteStateB)로 연결된다. 이 전이 화살표가 State임을 증명하는 결정타.

    C2

    데커레이터(Decorator)

    데커레이터 구조를 그려라. 이때 데커레이터가 Component를 구현하면서 동시에 멤버로 가지는 부분을 명확히 표시하라.

    정답 보기 ▸ C2
    UML C2구현 + 감쌈의 동시성
    classDiagram
    class Component {
        <<interface>>
        +operation()
    }
    class ConcreteComponent {
        +operation()
    }
    class Decorator {
        -wrapped : Component
        +operation()
    }
    class ConcreteDecorator {
        +operation()
        +addedBehavior()
    }
    Component <|.. ConcreteComponent
    Component <|.. Decorator : 구현
    Decorator o--> Component : 감쌈, 멤버 보유
    Decorator <|-- ConcreteDecorator
    채점 포인트

    핵심은 Decorator에서 나가는 두 화살표가 동시에 Component를 향하는 것. ① Component <|.. Decorator(점선 구현) — 데커레이터도 Component인 척해야 클라이언트가 동일하게 다룬다. ② Decorator o--> Component(합성, 감쌈) — 안에 다른 Component를 멤버로 들고 operation()을 위임한 뒤 자기 기능을 더한다.

    이 "구현 + 감쌈" 동시성이 빠지면 0점에 가깝다. 감쌈만 있고 구현이 없으면 단순 합성, 구현만 있고 감쌈이 없으면 그냥 상속/구현일 뿐 데커레이터가 아니다. wrapped 멤버 타입이 ConcreteComponent가 아니라 Component(추상)여야 데커레이터끼리도 중첩된다는 점도 표시하면 가점.

    C3

    커맨드(Command) — 4역할의 화살표

    Command, ConcreteCommand, Invoker, Receiver 4역할의 화살표 방향을 정확히 그려라.

    정답 보기 ▸ C3
    UML C3인보커는 리시버를 모른다
    classDiagram
    class Invoker {
        -command : Command
        +setCommand(c)
        +invoke()
    }
    class Command {
        <<interface>>
        +execute()
    }
    class ConcreteCommand {
        -receiver : Receiver
        +execute()
    }
    class Receiver {
        +action()
    }
    Invoker o--> Command : 커맨드만 안다
    Command <|.. ConcreteCommand : 구현
    ConcreteCommand --> Receiver : 실제 일 위임
    채점 포인트

    세 화살표의 방향이 전부 맞아야 한다. ① Invoker o--> Command — 인보커는 추상 Command만 보유하고 invoke()에서 execute()를 부른다. ② Command <|.. ConcreteCommand(점선 구현). ③ ConcreteCommand --> Receiver — execute() 안에서 receiver.action()으로 실제 일을 위임한다.

    가장 흔한 오답은 Invoker가 Receiver를 직접 가리키게 그리는 것. 인보커가 리시버를 모른다는 점(요청자와 수행자의 분리)이 Command의 존재 이유이자 채점의 핵심이다. 이 분리 덕분에 같은 인보커에 다른 커맨드를 끼워 undo, 큐잉, 매크로가 가능해진다.
