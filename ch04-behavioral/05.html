Sub-Chapter 05 · 행위 패턴

    템플릿 메서드 패턴,
    골격은 두고 단계만 바꾼다

    큰 흐름은 똑같은데 중간의 몇 단계만 다른 절차가 있다. 음료 끓이기, 데이터 처리 파이프라인, 게임 루프. 템플릿 메서드는 변하지 않는 골격을 상위 클래스에 한 번 적고, 변하는 단계만 하위 클래스가 채우게 한다.

    템플릿 메서드 패턴(Template Method Pattern)의 의도는 이렇다. 알고리즘의 뼈대(골격)를 상위 클래스의 한 메서드에 정의하고, 그 알고리즘의 일부 단계 구현은 서브클래스로 미룬다. 알고리즘의 구조는 그대로 유지한 채, 특정 단계만 서브클래스가 재정의하게 한다. 핵심은 "변하지 않는 전체 흐름"과 "흐름 안에서 달라지는 개별 단계"를 분리하되, 흐름의 통제권은 상위 클래스가 끝까지 쥐고 있다는 점이다. 하위 클래스는 흐름 자체를 바꿀 수 없고, 흐름이 호출하는 빈칸만 채운다.

    왜 필요한가? 여러 절차가 큰 줄기는 같고 세부 단계만 다른 경우가 자주 있다. 커피와 홍차를 끓이는 절차를 보자. 둘 다 "물을 끓이고 → 우려내고 → 잔에 붓고 → 첨가물을 넣는다"는 흐름은 같다. 다른 것은 우려내는 방식(커피는 필터로 내림, 홍차는 티백을 담금)과 첨가물(커피는 설탕/우유, 홍차는 레몬)뿐이다. 만약 커피 클래스와 홍차 클래스에 전체 절차를 각각 통째로 적으면, "물 끓이고 붓는" 공통 부분이 두 곳에 중복된다. 흐름을 바꿀 일이 생기면 양쪽을 똑같이 고쳐야 하고, 한쪽을 빠뜨리면 절차가 어긋난다. 템플릿 메서드는 공통 흐름을 상위에 한 번만 적어 중복을 제거하고, 흐름을 한 곳에서 통제한다.

    입사지원서 양식. 회사가 정한 지원서 양식에는 "이름 → 학력 → 경력 → 자기소개 → 서명" 순서가 고정되어 있다. 지원자(서브클래스)는 이 순서나 항목 구성을 마음대로 바꿀 수 없다 — 정해진 칸을 자기 내용으로 채울 뿐이다. 양식(상위 클래스의 템플릿 메서드)이 전체 구조를 통제하고, 각 칸의 내용(가변 단계)만 지원자가 다르게 적는다. 어떤 칸은 선택사항이라 비워 둘 수도 있는데(훅 메서드), 그래도 양식의 흐름 자체는 변하지 않는다. 템플릿 메서드가 정확히 이 구조다.

    구조 — 상위가 흐름을, 하위가 단계를

    구조는 상속 한 축으로 이뤄진다. AbstractClass가 핵심이다. 여기에 알고리즘의 골격을 담은 templateMethod()가 있는데, 이 메서드는 보통 final로 선언해 하위가 흐름을 바꾸지 못하게 막는다. templateMethod() 내부는 여러 단계를 정해진 순서로 호출하는데, 그 단계 중 변하는 것들은 추상 메서드(primitiveOp1(), primitiveOp2())로 선언만 해 둔다. ConcreteClass는 그 추상 단계들을 오버라이드해 자기만의 구현을 채운다.

    여기에 한 가지 장치가 더 있다. 훅(hook) 메서드다. 훅은 상위 클래스에 기본 구현(보통 아무 일도 안 하거나 단순 기본값)을 가진 메서드로, 하위가 필요하면 재정의할 수 있는 선택적 단계다. 예컨대 "고객이 첨가물을 원하는가?"를 묻는 customerWantsCondiments() 훅을 두면, 흐름은 이 훅의 반환값에 따라 첨가 단계를 건너뛸 수 있다. 추상 메서드는 "반드시 채워야 하는 빈칸"이고, 훅은 "원하면 끼어들 수 있는 선택지"라는 점에서 갈린다.

    UML 05템플릿 메서드 클래스 다이어그램 · 상위가 흐름, 하위가 단계
    classDiagram
    class AbstractClass {
        +templateMethod() final
        #primitiveOp1()
        #primitiveOp2()
        +hook()
    }
    class ConcreteClassA {
        #primitiveOp1()
        #primitiveOp2()
    }
    class ConcreteClassB {
        #primitiveOp1()
        #primitiveOp2()
        +hook()
    }
    AbstractClass <|-- ConcreteClassA
    AbstractClass <|-- ConcreteClassB

    templateMethod()는 AbstractClass에 한 번만 정의되고(final로 흐름 고정), 그 안에서 추상 단계 primitiveOp들을 정해진 순서로 호출한다. 실선 삼각 화살표(일반화, <|--)는 상속이다 — 합성이 아니라 상속이 이 패턴의 뼈대라는 점이 옵서버/스트래티지와 결정적으로 다르다. ConcreteClassB는 선택적 단계인 hook()까지 재정의한 경우다.

    참여자와 협력

    AbstractClass는 알고리즘의 골격인 templateMethod()와, 그 골격이 호출하는 추상 기본 단계(primitiveOp) 및 훅을 선언한다. ConcreteClass는 추상 단계를 자기 방식으로 구현해 알고리즘의 가변 부분을 채운다. 협력은 단순하면서도 방향이 독특하다 — 클라이언트가 ConcreteClass의 templateMethod()를 호출하면, 그 메서드는 상위 클래스에 정의된 흐름을 따라 진행하다가, 가변 단계에 이르면 하위 클래스가 오버라이드한 구현을 호출한다. 즉 제어의 주체는 어디까지나 상위의 흐름이고, 하위는 그 흐름이 부를 때만 등장한다.

    할리우드 원칙 — "Don't call us, we'll call you"

    이 제어 방향을 압축한 격언이 할리우드 원칙(Hollywood Principle)이다. "우리에게 전화하지 마라, 우리가 너에게 전화하겠다." 오디션을 본 배우가 제작사에 자꾸 전화를 거는 게 아니라, 제작사가 필요할 때 배우를 부르는 것이다. 템플릿 메서드에서 하위 클래스는 상위의 흐름을 호출하지 않는다 — 거꾸로 상위의 templateMethod()가 필요한 시점에 하위의 단계를 호출한다. 저수준 구성요소(하위 단계)가 고수준 흐름(상위)에 끼어드는 게 아니라, 고수준이 저수준을 부르는 이 방향이 의존성을 한쪽으로 정리해 결합을 낮춘다.

    코드 — 공통 흐름을 한 번만 적기

    음료 끓이기를 코드로 보자. 공통 흐름은 상위 Beverage에 한 번 적고, 우려내기와 첨가물만 하위가 채운다. 첨가물 단계는 훅으로 건너뛸 수 있게 한다.

    CODE 05음료 끓이기 템플릿 메서드 (골격 고정 + 훅)
    abstract class Beverage {
    // 알고리즘 골격 — final로 흐름을 못 바꾸게 고정
    public final void prepare() {
        boilWater();                       // 공통 단계
        brew();                            // 가변 단계 (추상)
        pourInCup();                       // 공통 단계
        if (customerWantsCondiments()) {   // 훅으로 분기
            addCondiments();               // 가변 단계 (추상)
        }
    }

    private void boilWater() { System.out.println("물을 끓인다"); }
    private void pourInCup() { System.out.println("잔에 붓는다"); }

    protected abstract void brew();          // 반드시 채워야 하는 빈칸
    protected abstract void addCondiments();

    // 훅 — 기본은 true, 하위가 원하면 재정의
    protected boolean customerWantsCondiments() { return true; }
}

class Coffee extends Beverage {
    protected void brew() { System.out.println("필터로 커피를 내린다"); }
    protected void addCondiments() { System.out.println("설탕과 우유를 넣는다"); }
}

class Tea extends Beverage {
    protected void brew() { System.out.println("티백을 우린다"); }
    protected void addCondiments() { System.out.println("레몬을 넣는다"); }
    // 훅 재정의 — 이 차는 첨가물을 넣지 않는다
    protected boolean customerWantsCondiments() { return false; }
}

// 사용 — 흐름은 상위가, 단계는 하위가
new Coffee().prepare();   // 물끓임 -> 내림 -> 부음 -> 설탕/우유
new Tea().prepare();      // 물끓임 -> 우림 -> 부음 (첨가물 생략)

    prepare()의 흐름은 Beverage에 단 한 번 적혀 있고, Coffee와 Tea는 brew()와 addCondiments()라는 빈칸만 다르게 채운다. 공통 단계(물 끓이기, 붓기)는 중복 없이 상위에 모여 있다. Tea는 훅을 false로 재정의해 첨가 단계를 통째로 건너뛴다 — 흐름 자체는 손대지 않은 채로.

    결과 — 무엇을 얻고 무엇을 치르는가

    참여자

    AbstractClass(templateMethod 골격 + 추상 단계 + 훅), ConcreteClass(가변 단계 구현)

    장점

    공통 흐름 중복 제거, 흐름을 한 곳에서 통제, 가변 단계만 확장, 할리우드 원칙으로 제어 역전

    단점

    상속 기반이라 컴파일 시점에 고정, 단계가 많아지면 추적 어려움, 흐름 변경 시 상위 수정 필요

    Template Method vs Strategy — 같은 목표, 다른 수단

    둘 다 "변하는 부분만 분리한다"는 목표를 공유한다. 그래서 헷갈린다. 그러나 분리하는 수단이 정반대다. 템플릿 메서드는 상속으로 가변 단계를 하위 클래스에 미루고, 스트래티지는 합성으로 알고리즘 객체를 주입한다. 이 차이가 "언제 결정되는가"와 "얼마나 바꿀 수 있는가"를 가른다.

    비교 축템플릿 메서드 (상속)스트래티지 (합성)
    분리 수단상속 — 가변 단계를 서브클래스가 오버라이드합성 — 알고리즘을 객체로 주입(위임)
    결정 시점컴파일 시점 고정 (어떤 하위 클래스를 쓸지 정해짐)런타임 교체 (전략 필드를 갈아끼움)
    변하는 단위알고리즘 안의 일부 단계만 다름알고리즘 전체를 통째로 교체
    흐름 통제상위 클래스가 전체 흐름을 끝까지 쥠Context가 위임만, 흐름은 단순
    제어 방향할리우드 원칙(상위가 하위를 부름)클라이언트가 전략을 골라 주입
    한 줄"흐름은 고정, 단계만 오버라이드""행위 전체를 갈아끼움"

    이 표는 빠른 회상용이고, 결정적 직관은 이렇다 — 한 알고리즘의 골격은 그대로 두고 빈칸 몇 개만 바꾸고 싶으면 템플릿 메서드, 알고리즘 자체를 통째로 다른 것으로 런타임에 바꾸고 싶으면 스트래티지다. "상속보다 합성"이라는 원칙 때문에 유연성은 스트래티지가 높지만, 흐름의 중복을 한곳에 모으고 통제하는 힘은 템플릿 메서드가 강하다.

    시험 함정. ① 할리우드 원칙("Don't call us, we'll call you")이 키워드다 — 하위가 상위를 부르는 게 아니라 상위 흐름이 하위 단계를 부른다(제어 역전). ② templateMethod()는 보통 final로 두어 흐름을 못 바꾸게 한다. ③ 추상 단계 vs 훅 구분 — 추상 단계는 반드시 채워야 하고, 훅은 기본 구현이 있어 선택적으로 재정의한다. ④ 최빈출은 Template Method(상속·컴파일 고정) vs Strategy(합성·런타임 교체) 비교다.

    다음으로 — 흐름의 분리에서 순회의 분리로

    템플릿 메서드는 알고리즘의 골격을 상속으로 고정하고 단계만 바꿨다. 분리한 것은 알고리즘의 가변 단계다. 마지막 sub-chapter의 이터레이터 패턴(Iterator Pattern)은 또 다른 책임을 떼어 낸다 — 컬렉션의 순회 책임이다. 데이터를 담는 일과 그것을 하나씩 훑는 일을 별도 객체로 나눠, 컬렉션의 내부 구조를 감춘 채 순차 접근하게 만든다. 변하는 부분을 분리한다는 행위 패턴의 큰 그림이 순회라는 마지막 책임에서 어떻게 마무리되는지 이어서 보자.
