Sub-Chapter 02 · 헷갈리는 6쌍

    헷갈리는 6쌍,
    구조는 같고 의도가 다르다

    시험에서 끝까지 흔들리는 건 정의가 아니라 "구별"이다. 구조가 거의 같은 여섯 쌍을, 공통점과 결정적 차이로 가른다. 표만 외우면 변형 문제에서 무너진다.

    앞 sub-chapter의 의사결정 흐름이 후보를 둘로 좁혀줬다면, 마지막 한 걸음은 그 둘 중 어느 쪽이냐를 가리는 일이다. 그런데 시험에 단골로 나오는 쌍들은 하나같이 클래스 다이어그램이 거의 같다. 전략과 상태는 구조가 사실상 동일하고, 데커레이터와 컴포지트는 둘 다 자기 자신을 재귀로 품으며, 어댑터와 데커레이터는 둘 다 객체를 감싼다. 겉모습으로는 구별되지 않는다. 차이는 항상 "무엇을 풀려고 태어났는가"라는 의도(intent)에 있다. 아래 여섯 쌍을 공통점과 결정적 차이로 가르되, 각 차이의 "왜"를 함께 익힌다.

    쌍 1 — 전략(Strategy) 대 상태(State)

    이 둘은 클래스 다이어그램이 같다. 둘 다 Context가 어떤 인터페이스에 작업을 위임하고, 그 인터페이스의 구현체를 갈아끼운다. 차이는 "누가 그 교체를 통제하는가"다. 전략은 외부(클라이언트)가 어떤 알고리즘을 쓸지 선택해 Context에 주입한다(예: 정렬 방식을 사용자가 고름). 상태는 상태 객체 스스로가 다음 상태로 전이한다(예: 신호등이 초록에서 노랑으로 알아서 넘어감). 즉 전략은 "교체 가능한 알고리즘", 상태는 "스스로 전이하는 행동"이다.

    구분전략 (Strategy)상태 (State)
    공통점Context가 인터페이스에 위임하고 구현체를 갈아끼우는 동일 구조
    결정적 차이외부가 알고리즘을 선택해 주입상태가 스스로 다음 상태로 전이
    전형 예정렬/할인/결제 방식 교체신호등, 주문 상태 머신

    쌍 2 — 템플릿 메서드(Template Method) 대 전략(Strategy)

    둘 다 "변하는 부분만 분리한다"는 목표를 공유한다. 전체 흐름은 두되 일부 단계만 달라지게 만든다. 차이는 그 분리를 상속으로 하느냐 합성으로 하느냐다. 템플릿 메서드는 상위 클래스가 흐름(템플릿)을 고정하고 달라지는 단계를 추상 메서드로 비워, 서브클래스가 상속으로 채운다. 따라서 어떤 변형을 쓸지는 컴파일 시점에 굳는다. 전략은 변하는 알고리즘을 별도 객체로 빼 합성으로 주입하므로, 런타임에 교체할 수 있다. "흐름은 고정, 단계만 다름 + 컴파일 고정"이면 템플릿 메서드, "알고리즘 통째 교체 + 런타임"이면 전략이다.

    구분템플릿 메서드전략 (Strategy)
    공통점변하는 부분만 분리해 재사용
    결정적 차이상속 기반, 컴파일 시점 고정합성 기반, 런타임 교체
    유연성흐름 고정, 단계만 오버라이드알고리즘 통째 갈아끼움

    쌍 3 — 데커레이터(Decorator) 대 상속

    둘 다 기능을 확장하는 수단이다. 차이는 확장이 동적이냐 정적이냐다. 상속은 컴파일 시점에 부모-자식 관계가 굳는 정적 확장이다. 그래서 기능 조합이 늘어나면 "커피+우유", "커피+우유+시럽", "커피+시럽" 같은 모든 경우의 수만큼 서브클래스가 폭발한다(클래스 폭발). 데커레이터는 같은 인터페이스를 유지한 채 객체를 런타임에 겹겹이 감싸므로, 필요한 기능만 그때그때 조합한다. 조합 폭발 없이 동적으로 책임을 더한다는 점이 핵심이다.

    구분데커레이터상속
    공통점기존 객체에 기능을 추가/확장
    결정적 차이동적 조합(런타임에 감쌈)정적 고정(컴파일 시점)
    약점감싸는 층이 깊어지면 추적 어려움조합 수만큼 서브클래스 폭발

    쌍 4 — 데커레이터(Decorator) 대 컴포지트(Composite)

    둘 다 자기 자신을 재귀로 품는 합성 구조라 다이어그램이 닮았다. 차이는 "무엇을 위해 감싸느냐"와 "몇 개를 품느냐"다. 데커레이터는 하나의 컴포넌트를 감싸 기능을 더한다(책임 추가가 목적). 컴포지트는 여럿의 자식을 모아 트리를 만든다(전체-부분 표현이 목적). 즉 데커레이터의 재귀는 "기능을 쌓는 한 줄 사슬"이고, 컴포지트의 재귀는 "여러 갈래로 뻗는 나무"다.

    구분데커레이터컴포지트
    공통점자기 자신을 재귀로 품는 합성 구조
    결정적 차이하나를 감싸 기능 추가여럿을 모아 트리 구성
    목적책임의 동적 추가전체-부분 계층 표현

    쌍 5 — 어댑터(Adapter) 대 데커레이터(Decorator)

    둘 다 객체를 감싼다. 차이는 감싼 뒤 인터페이스를 바꾸느냐 유지하느냐다. 어댑터는 호환되지 않는 인터페이스를 다른 인터페이스로 변환한다. 목적은 "협력 가능하게 만들기"이지 기능 추가가 아니다. 데커레이터는 같은 인터페이스를 유지한 채 기능만 더한다. 한 문장으로, 어댑터는 "모양을 바꿔 끼우는 변환기", 데커레이터는 "모양은 그대로 두고 기능을 입히는 옷"이다.

    구분어댑터데커레이터
    공통점대상 객체를 감싸 위임
    결정적 차이인터페이스 변환(호환시킴)인터페이스 유지 + 기능 추가
    목적맞지 않는 것을 협력시키기같은 계약으로 책임 더하기

    쌍 6 — 팩토리 메서드(Factory Method) 대 추상 팩토리(Abstract Factory)

    둘 다 객체 생성을 캡슐화해 new를 사용처에서 떼어낸다. 차이는 상속으로 단일 제품을 만드느냐, 합성으로 제품군을 만드느냐다. 팩토리 메서드는 하나의 메서드를 서브클래스가 오버라이드해 단일 제품의 종류를 결정한다(상속 기반). 추상 팩토리는 한 팩토리 객체가 서로 관련된 제품군 전체를 일관되게 생성한다(합성 기반). 예를 들어 버튼 하나를 만드는 결정이면 팩토리 메서드, 버튼+체크박스+창틀을 한 테마로 일관되게 만들어야 하면 추상 팩토리다.

    구분팩토리 메서드추상 팩토리
    공통점객체 생성을 캡슐화(OCP 지원)
    결정적 차이메서드 상속으로 단일 제품객체 합성으로 제품군 전체
    규모제품 하나의 종류 결정관련 제품들을 일관되게 묶음

    한눈에 보는 종합 비교

    여섯 쌍을 한 표로 모은다. 빠른 회상용이며, 각 차이의 근거는 위 본문에서 "왜"와 함께 익혀야 한다.

    비교공통점결정적 차이
    전략 vs 상태Context가 위임하는 동일 구조전략=외부가 알고리즘 선택 / 상태=스스로 전이
    템플릿 메서드 vs 전략변하는 부분만 분리템플릿=상속(컴파일 고정) / 전략=합성(런타임 교체)
    데커레이터 vs 상속기능 확장데커레이터=동적 조합 / 상속=정적 고정, 조합 폭발
    데커레이터 vs 컴포지트재귀 합성 구조데커레이터=하나 감싸 기능추가 / 컴포지트=여럿 모아 트리
    어댑터 vs 데커레이터객체를 감쌈어댑터=인터페이스 변환 / 데커레이터=유지+기능추가
    팩토리 메서드 vs 추상 팩토리생성 캡슐화FM=상속으로 단일 제품 / AF=합성으로 제품군

    "한 줄 요약" 모음

    시험장 직전 속독용 한 줄 요약이다. 각 줄을 보고 본문의 "왜"가 떠오르면 준비가 된 것이다.

    • 전략 vs 상태 — 교체를 외부가 하면 전략, 스스로 전이하면 상태.
    • 템플릿 vs 전략 — 상속으로 단계만 채우면 템플릿, 합성으로 통째 갈면 전략.
    • 데커레이터 vs 상속 — 런타임 조합이면 데커레이터, 컴파일 고정이면 상속(조합 폭발).
    • 데커레이터 vs 컴포지트 — 하나 감싸 기능 추가면 데커레이터, 여럿 모아 트리면 컴포지트.
    • 어댑터 vs 데커레이터 — 인터페이스를 바꾸면 어댑터, 유지하며 기능 더하면 데커레이터.
    • 팩토리 메서드 vs 추상 팩토리 — 단일 제품이면 FM, 제품군 전체면 AF.
    구별의 열쇠

    구조가 같으면 의도(intent)로 가른다 — 정의가 아니라 목적

    반복 축

    상속 대 합성 / 컴파일 고정 대 런타임 교체가 거듭 등장

    마무리 원칙

    둘로 좁혀지면 OCP와 "상속보다 합성"으로 결정

    시험 함정. 표만 외우지 말고 "왜"를 이해하라. 표는 빠른 회상용일 뿐, 시나리오를 변형하면(예: "정렬 방식을 사용자가 고른다" 대 "주문이 결제완료로 넘어간다") 표만 외운 머리는 흔들린다. 각 쌍의 결정적 차이가 왜 그렇게 갈리는지 — 누가 교체를 통제하나, 상속이냐 합성이냐, 인터페이스를 바꾸나 유지하나 — 를 근거째 익혀야 응용 문제에 답할 수 있다. 또한 여섯 쌍을 관통하는 두 축, 상속 대 합성과 컴파일 고정 대 런타임 교체를 알면 새 쌍을 만나도 같은 방식으로 가를 수 있다.

    이로써 여섯 챕터를 관통한 복습이 마무리된다. 기초(설계 원칙)에서 출발해 생성, 구조, 행위 패턴을 거쳐, 시스템과 객체 설계로 패턴이 투입되는 자리를 짚고, 마지막으로 "어떤 상황에 무엇을 쓸 것인가"의 선택과 구별에 이르렀다. 모든 패턴이 결국 OCP와 "상속보다 합성"이라는 두 원칙을 어떻게 실현하는지로 수렴한다는 사실을, 시험장에서 떠올릴 수 있으면 된다.
