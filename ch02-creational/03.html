Sub-Chapter 03 · 생성 패턴

    추상 팩토리 패턴,
    제품군 전체를 한 세트로

    버튼만 따로, 체크박스만 따로 만들면 맥 버튼에 윈도우 체크박스가 섞일 수 있다. 추상 팩토리는 서로 어울려야 하는 제품들을 한 팩토리가 통째로 책임지게 해, 일관성을 구조로 강제한다.

    추상 팩토리 패턴(Abstract Factory Pattern)의 의도는 이렇다. 서로 관련되거나 의존하는 제품군(family) 전체를, 구체 클래스를 지정하지 않고 생성하는 인터페이스를 제공한다. 앞 페이지의 팩토리 메서드가 "제품 하나"의 생성을 책임졌다면, 추상 팩토리는 "함께 어울려야 하는 여러 제품"을 한 묶음으로 만든다. 핵심 단어는 제품군과 일관성이다.

    왜 제품군 단위로 묶어야 하는가? GUI 툴킷을 떠올려 보자. 같은 화면 안의 버튼, 체크박스, 스크롤바는 모두 같은 운영체제 스타일이어야 한다. 맥 스타일 버튼 옆에 윈도우 스타일 체크박스가 놓이면 어색할 뿐 아니라 동작 규칙도 어긋난다. 만약 각 위젯을 따로따로 생성하면, 코드 곳곳에서 실수로 스타일을 섞을 위험이 늘 존재한다. 추상 팩토리는 "한 팩토리가 한 제품군 전체를 만든다"는 규칙을 세워, MacFactory를 쓰는 한 모든 위젯이 자동으로 맥 스타일로 통일되게 한다. 일관성을 사람의 주의력이 아니라 구조로 보장하는 것이다.

    한 디자이너가 꾸민 거실 세트. 가구를 하나씩 따로 사면 모던 소파에 클래식 테이블이 섞여 통일감이 깨지기 쉽다. 대신 "북유럽 스타일 세트", "인더스트리얼 스타일 세트"처럼 한 컨셉으로 묶인 패키지를 고르면, 소파, 테이블, 조명이 모두 같은 톤으로 일관되게 따라온다. 컨셉(팩토리)을 한 번 고르는 순간 제품군 전체가 결정된다. 다른 컨셉으로 바꾸고 싶으면 패키지만 통째로 교체하면 된다.

    구조 — 한 팩토리가 제품군을 통째로 만든다

    추상 AbstractFactory는 제품군의 각 제품을 만드는 메서드(createButton(), createCheckbox())를 선언한다. 이를 구현한 WinFactory와 MacFactory는 각자의 스타일에 맞는 구체 제품을 돌려준다. 클라이언트는 어떤 구체 팩토리를 쓰는지만 한 번 정하고, 그 뒤로는 추상 인터페이스에만 의존한다. 그래서 윈도우에서 맥으로 옮길 때 코드가 바꾸는 곳은 "어느 팩토리를 주입할지" 단 한 줄뿐이다.

    UML 03추상 팩토리 · 한 팩토리 = 한 제품군
    classDiagram
    class AbstractFactory {
        +createButton() Button
        +createCheckbox() Checkbox
    }
    class WinFactory {
        +createButton() Button
        +createCheckbox() Checkbox
    }
    class MacFactory {
        +createButton() Button
        +createCheckbox() Checkbox
    }
    AbstractFactory <|.. WinFactory
    AbstractFactory <|.. MacFactory

    한 구체 팩토리가 버튼과 체크박스를 모두 책임진다. MacFactory를 쓰는 한 둘 다 맥 스타일로 나온다 — 제품군의 일관성이 팩토리 선택 한 번으로 강제된다. 각 create 메서드 구현 자체가 사실상 팩토리 메서드라는 점에 주목하라.

    코드 — 팩토리를 주입하면 제품군이 따라온다

    클라이언트는 어떤 구체 팩토리를 받았는지 신경 쓰지 않고, 추상 팩토리의 메서드만 호출한다. 같은 코드가 주입된 팩토리에 따라 윈도우 세트 또는 맥 세트를 일관되게 만들어 낸다. 구체 클래스 이름은 클라이언트 코드 어디에도 등장하지 않는다.

    CODE 03GUI 툴킷 — 팩토리 합성으로 제품군 통일
    interface GUIFactory {
    Button   createButton();
    Checkbox createCheckbox();
}

class MacFactory implements GUIFactory {
    public Button   createButton()   { return new MacButton(); }
    public Checkbox createCheckbox() { return new MacCheckbox(); }
}

class WinFactory implements GUIFactory {
    public Button   createButton()   { return new WinButton(); }
    public Checkbox createCheckbox() { return new WinCheckbox(); }
}

// 클라이언트: 팩토리를 합성으로 주입받아 제품군 전체를 일관되게 생성
class Dialog {
    private final GUIFactory factory;      // 어떤 제품군인지 주입
    Dialog(GUIFactory factory) { this.factory = factory; }

    void render() {
        Button   ok   = factory.createButton();    // 둘 다 같은 스타일로
        Checkbox keep = factory.createCheckbox();  // 자동 통일된다
        ok.paint();
        keep.paint();
    }
}

    Dialog는 구체 위젯 클래스를 전혀 모른다. 생성자에 MacFactory를 넣으면 맥 세트가, WinFactory를 넣으면 윈도우 세트가 나온다. 운영체제를 바꾸는 일이 "주입하는 팩토리 한 줄 교체"로 끝난다.

    참여자와 결과

    참여자

    AbstractFactory / ConcreteFactory(Win, Mac) / AbstractProduct(Button, Checkbox) / ConcreteProduct / Client

    장점

    제품군의 일관성 보장, 구체 클래스 격리, 제품군 교체가 팩토리 한 줄 교체로 끝남

    단점

    제품 종류(메서드)를 추가하면 모든 팩토리를 고쳐야 함 — 제품군 확장은 쉽지만 제품 항목 확장은 어려움

    Factory Method vs Abstract Factory — 최빈출 비교

    이 두 패턴의 구분은 생성 패턴 시험에서 가장 단골이다. 둘 다 "생성을 캡슐화해 구체 클래스를 숨긴다"는 같은 목표를 공유하지만, 무엇을 만드느냐(단일 제품 대 제품군)와 어떻게 위임하느냐(상속 대 합성)에서 갈린다. 표로 핵심을 잡되, 표만 외우면 시나리오 변형 문제에서 흔들리므로 아래 산문 설명까지 함께 이해해야 한다.

    기준팩토리 메서드 (Factory Method)추상 팩토리 (Abstract Factory)
    만드는 대상제품 하나를 만든다제품군 전체를 만든다
    위임 수단상속 — 서브클래스가 오버라이드로 결정합성 — 팩토리 객체를 주입
    단위클래스(메서드) 단위객체 단위
    확장 방향새 제품 = 새 서브클래스 추가새 제품군 = 새 팩토리 추가
    관계그 자체로 완결각 메서드 구현이 흔히 팩토리 메서드로 됨
    한 줄 요약메서드 하나로 한 제품객체 하나로 제품군 전체

    표를 풀어 설명하면 이렇다. 팩토리 메서드는 "무엇을 만들지"의 결정권을 상속으로 아래에 내려보낸다. 결정의 단위는 메서드 하나이고, 대상은 보통 제품 하나다. 새 제품을 추가하려면 새 서브클래스를 만든다. 반면 추상 팩토리는 "어떤 제품군을 쓸지"를 합성으로 주입한다. 팩토리 객체 하나를 갈아끼우면 그 안의 여러 제품이 한꺼번에 일관되게 바뀐다.

    둘은 경쟁 관계라기보다 층위가 다른 도구다. 실제로 추상 팩토리의 각 createXxx() 메서드 구현은 종종 그 자체가 팩토리 메서드 형태를 띤다. 즉 추상 팩토리는 팩토리 메서드들의 묶음으로 구현되곤 한다. 그래서 시험에서 "이 시나리오에서 더 적합한 것은?"을 물으면, 만들 대상이 제품 하나이고 서브클래스마다 다른 제품을 내면 팩토리 메서드, 여러 제품이 세트로 일관되어야 하고 세트 통째로 교체해야 하면 추상 팩토리로 판단한다.

    시험 함정. ① "단일 제품 = Factory Method, 제품군 = Abstract Factory"가 1차 판별 기준이다. ② 위임 수단이 상속이냐(FM) 합성이냐(AF)도 결정적 차이다. ③ 추상 팩토리의 약점 — 새 제품 항목(예: 스크롤바)을 추가하면 모든 팩토리 인터페이스와 구현을 고쳐야 한다(제품군 추가는 쉽지만 제품 항목 추가는 OCP를 깬다). ④ 추상 팩토리가 내부적으로 팩토리 메서드로 구현된다는 관계도 출제 포인트다.

    여기까지가 생성 패턴 3종이다. 싱글톤은 생성 횟수를, 팩토리 메서드는 단일 제품의 종류를, 추상 팩토리는 제품군 전체를 통제했다. 셋 모두 new를 사용하는 코드로부터 생성 책임을 떼어 내 변경을 한곳에 가둔다는 같은 정신을 공유한다. 다음 장에서는 "이미 만들어진 객체들을 어떻게 조립할 것인가"를 다루는 구조 패턴으로 넘어간다.
