Sub-Chapter 01 · 행위 패턴

    스트래티지 패턴,
    알고리즘을 갈아끼우다

    같은 일을 하는 방법이 여러 개고, 어떤 방법을 쓸지 런타임에 정해야 한다. 결제 수단, 정렬 방식, 할인 정책. 스트래티지는 이 "변하는 방법"을 객체로 뽑아내, 사용하는 코드를 건드리지 않고도 통째로 바꿔 끼우게 만든다.

    스트래티지 패턴(Strategy Pattern)의 의도는 이렇다. 알고리즘군(family of algorithms)을 각각 캡슐화해 서로 교체 가능하게 만들고, 알고리즘을 사용하는 클라이언트와 독립적으로 알고리즘을 바꿀 수 있게 한다. 핵심은 "같은 목적을 이루는 여러 방법"을 하나하나 별도 객체로 떼어 내고, 그 객체들이 같은 인터페이스를 공유하게 하는 것이다. 그러면 사용하는 쪽은 인터페이스만 알면 되고, 구체적인 방법은 언제든 다른 것으로 바꿔 끼울 수 있다.

    왜 필요한가? 행위가 여러 갈래로 나뉘는 코드를 가장 손쉽게 짜는 방법은 조건 분기다. 결제 처리를 예로 들면 if(카드) ... else if(계좌이체) ... else if(포인트) ... 같은 식이다. 문제는 결제 수단이 하나 늘 때마다 이 분기문을 찾아 또 한 가지를 추가해야 한다는 점이다. 이는 개방-폐쇄 원칙(OCP, Open-Closed Principle) 위반이다 — 기능 확장을 위해 기존 코드를 자꾸 열어 고쳐야 하기 때문이다. 게다가 분기가 여러 메서드에 흩어져 있으면 한 곳을 빠뜨리는 실수도 잦다. 스트래티지는 각 방법을 독립된 객체로 만들어, 새 방법은 새 클래스를 더하는 것으로 끝나게 한다. 기존 코드는 닫힌 채로 둔 채 확장만 일어난다.

    여행 이동 수단 고르기. 공항에서 시내로 갈 때 택시, 지하철, 공항버스라는 선택지가 있다. "시내로 간다"는 목적은 같지만 방법은 제각각이다. 당신(클라이언트)은 그날의 상황 — 짐의 양, 예산, 시간 — 을 보고 수단 하나를 고른다. 일단 고르면 그 수단의 세부(노선, 요금 계산)는 그 수단이 알아서 한다. 새 수단(공유 킥보드)이 생겨도 당신의 "이동한다"는 행동 자체는 바뀌지 않는다. 스트래티지가 정확히 이 구조다. Context는 "이동한다"는 목적, 각 교통수단이 ConcreteStrategy, 당신이 수단을 고르는 행위가 setStrategy()다.

    구조 — 행위를 합성으로 주입한다

    구조는 세 부분으로 이뤄진다. 첫째, 모든 방법이 공유하는 공통 인터페이스 Strategy가 있다(예: algorithm()). 둘째, 그 인터페이스를 구현한 구체 전략들 ConcreteStrategyA, ConcreteStrategyB가 각자의 방법을 담는다. 셋째, 이 전략을 사용하는 Context는 구체 전략이 아니라 Strategy 인터페이스 타입의 필드만 가진다. 그리고 자기 일을 직접 하지 않고 그 전략 객체에 위임(delegation)한다. 즉 Context는 "무엇을 할지"는 알되 "어떻게 할지"는 전략에 떠넘긴다.

    여기서 결정적인 점은 Context가 전략을 상속이 아니라 합성(composition)으로 보유한다는 것이다. 상속이라면 전략을 컴파일 시점에 못 박아야 하지만, 합성이면 필드를 바꿔 끼우는 것만으로 런타임에 행위를 교체할 수 있다. "상속보다 합성"이라는 객체지향 설계 원칙이 그대로 드러나는 자리다.

    Context는 Strategy 인터페이스에만 의존(o--> 합성 연관)하고, 실제 일은 주입된 구체 전략의 algorithm()에 넘긴다. 새 전략은 점선 화살표(실현, ..|>)로 인터페이스를 구현하는 클래스를 하나 더 추가하기만 하면 된다 — 기존 코드는 손대지 않는다.

    참여자와 협력

    Strategy는 모든 알고리즘에 공통인 인터페이스를 선언한다. ConcreteStrategy는 그 인터페이스로 실제 알고리즘을 구현한다. Context는 Strategy 참조를 들고 있다가, 클라이언트가 설정한 전략에 작업을 위임한다. 협력의 흐름은 단순하다 — 클라이언트가 원하는 ConcreteStrategy를 만들어 Context에 주입(setStrategy)하고, 이후 Context.execute()가 호출되면 Context는 내부적으로 보관한 전략의 algorithm()을 부른다. 전략을 고르는 주체는 어디까지나 외부의 클라이언트다. 이 "외부가 고른다"는 점이 뒤에서 볼 스테이트 패턴과의 결정적 차이가 된다.

    코드 — 분기를 객체로 대체하기

    할인 정책을 예로 보자. 분기문 버전은 정책이 늘 때마다 calculate()를 열어 고쳐야 한다. 스트래티지 버전은 정책마다 클래스를 두고, 가격 계산기는 어떤 정책이 꽂혔는지 모른 채 위임만 한다.

    CODE 01할인 정책 스트래티지 (런타임 교체)
    // 공통 인터페이스 — 모든 할인 정책이 공유
interface DiscountStrategy {
    int discount(int price);
}

// 구체 전략들 — 각자 한 가지 방법만 책임
class NoDiscount implements DiscountStrategy {
    public int discount(int price) { return price; }
}
class RateDiscount implements DiscountStrategy {
    private final double rate;
    RateDiscount(double rate) { this.rate = rate; }
    public int discount(int price) { return (int)(price * (1 - rate)); }
}

// Context — 전략을 합성으로 보유하고 위임만 한다
class Checkout {
    private DiscountStrategy strategy = new NoDiscount();
    public void setStrategy(DiscountStrategy s) { this.strategy = s; }  // 런타임 교체
    public int finalPrice(int price) { return strategy.discount(price); } // 위임
}

// 사용 — 클라이언트가 전략을 골라 갈아끼운다
Checkout c = new Checkout();
c.setStrategy(new RateDiscount(0.2));   // 20% 할인으로 교체
int paid = c.finalPrice(10000);          // 8000

    새 할인 정책(예: 정액 할인)을 추가하려면 DiscountStrategy를 구현하는 클래스를 하나 더 만들면 끝이다. Checkout 코드는 전혀 바뀌지 않는다 — 확장에는 열려 있고 수정에는 닫혀 있다(OCP).

    결과 — 무엇을 얻고 무엇을 치르는가

    참여자

    Strategy(공통 인터페이스), ConcreteStrategy(개별 알고리즘), Context(전략 보유 + 위임)

    장점

    알고리즘을 런타임에 교체, 분기문 제거, OCP 준수(새 전략 = 새 클래스), 알고리즘 단위 테스트 용이

    단점

    전략 수만큼 클래스 증가, 클라이언트가 전략들의 차이를 알아야 적절히 선택 가능

    시험 함정. ① 스트래티지는 행위를 합성으로 주입한다 — 상속(컴파일 시점 고정)이 아니라 위임(런타임 교체)이 핵심. ② 전략을 고르는 주체는 외부 클라이언트다. ③ 가장 단골은 Strategy vs State 비교다. 클래스 다이어그램이 거의 똑같아(Context가 인터페이스에 위임) 구조만으로는 구분이 안 된다. 차이는 의도에 있다 — 다음 sub-chapter에서 결판낸다.

    다음으로 — Strategy vs State 예고

    스트래티지의 클래스 다이어그램을 머릿속에 새겨 두자. Context가 인터페이스 타입 필드를 들고 위임하는 모양. 다음 sub-chapter의 스테이트 패턴(State Pattern)은 이 그림과 거의 동일한 구조를 갖는다. 그런데도 둘은 전혀 다른 패턴이다. 핵심 차이를 미리 한 줄로 박아 두면 — 스트래티지는 "외부가 전략을 골라 갈아끼운다", 스테이트는 "상태 객체가 스스로 다음 상태로 전이한다". 같은 뼈대에 다른 의도. 그 차이가 어떻게 코드로 갈라지는지 다음 장에서 충실히 비교한다.
